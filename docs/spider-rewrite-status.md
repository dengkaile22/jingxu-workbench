# 选品爬虫重写说明与验证状态

**范围：** `src/JingXu.Workbench.Py/JingXu.Spider`（抖音/快手带货商品提取）+ 工作台侧集成
**相关提交：** `62f9bfb`、`286cca6`、`3ccb1e0`、`c8d3166`

---

## 1. 为什么重写

用户实测反馈：抖音日志显示「已处理 57 个视频，累计发现带货商品 0 件」。

排查后的结论是**失败方式有问题**，而不是某个字段名写错：

旧实现把字段路径写死在两个 crawler 里（抖音只找 `anchor_info` / `promotions` /
`anchors`）。平台一旦改字段名或把商品挪到新位置，提取就**静默返回空**——日志只有
计数，没有任何可排查信息，连「是没挂商品还是解析失败」都分辨不出。

因此重写的目标不是猜新字段名（无法访问真实平台验证），而是把**静默失败变成
可定位问题**。

---

## 2. 提取：分层 + 全树扫描

新增 `core/extraction.py`，三层逐级放宽：

| 层 | 做法 | 覆盖场景 |
|----|------|----------|
| 已知路径 | 平台候选路径登记表（抖音 17 条 / 快手 11 条），逐条尝试并记录命中/为空 | 常规结构、`a.b[0].c` 形式、商品信息塞在 JSON 字符串里（`anchor_info.extra`） |
| 全树扫描 | 递归遍历视频 JSON，按商品特征键（`product_id`/`goods_id`/`promotion_id` 等）找出候选节点；跳过 `video`/`music`/`cover` 等大子树，带节点预算 | **平台改字段名或挪位置** |
| 候选评分 | 按特征键数量打分，对视频/用户字段做误报惩罚 | 抑制误报 |

始终产出 `ExtractionDiagnostic`：命中路径、为空路径、扫描节点数、候选数、
扫描命中路径，以及一行式摘要。

### 已实测（合成样本）

| 场景 | 结果 |
|------|------|
| 旧结构 `anchor_info.extra` | 命中，`3990` 分 → `¥39.90` 正确 |
| **字段挪到全新位置** | 已知路径全空，**全树扫描救回**（旧实现必然漏掉） |
| 确实没挂商品 | 不误报，结论为「该视频很可能确实没有挂商品」 |

### 顺带修掉的假数据缺陷

外层 `anchor_info.title` 的值是「商品」这类**占位说明**，旧逻辑会把它当成第二个
商品，导致每条视频多出一条名为「商品」的记录。已加通用占位黑名单
（商品/购物车/小黄车/去看看/立即购买/shop…）。

## 3. 环境与登录态治理

新增 `core/diagnostics.py`。

### 运行前自检 `run_preflight`

检查项：解释器版本（<3.9 阻断）、依赖模块、Chromium 内核、**profile 独占锁**、
无头模式与扫码的矛盾、各平台登录态。每项给出「问题 + 建议」，阻断级问题直接
停止运行（退出码 2）。

其中 profile 锁检查对应此前实测的崩溃：两个 Chromium 实例抢同一档案目录。

### 登录态 / Cookie 记录

Chromium 无法低成本读取 cookie 判断登录，因此改为**行为证据**：从页面文本识别
登录引导/验证码标记，把结果写入 `<数据目录>/Spider/login_state.json`
（状态、明细、观测时间、最近正常时间），并翻译为一句可读状态：

```
上次抓取要求登录（2026-09-20 15:05:42），登录态可能已失效，请重新扫码
```

### 运行后诊断 `run_diagnosis`

区分两种**结论不同**的情况并给不同建议：

- 「扫描 1200 个节点、3 个候选」→ 有候选但取不出 → 平台字段结构可能已变化
- 「扫描 900 个节点、0 个候选」→ 这些视频很可能确实没挂商品

并识别登录失效、风控、无视频、无跨账号交集、用户取消。

## 4. 打通到工作台

- 两个 crawler 逐条记录 `[未提取到商品]` 及原因，不再只有计数
- `cli.py` 输出自检结果与诊断；诊断写入 `--json-out` 的 `diagnostics` 段
  （**既有字段全部保留**，不破坏接口）
- 工作台 `SpiderDiagnosticsView` 解析该段：**阻断级诊断压过「抓取完成」**显示在
  主提示位，并展示「扫描 N 个视频 · 含商品 M 个」；结果落盘一并保存
- 失败时把子进程输出尾部 400 行留档到 `logs/spider-*.log`，失败信息里给出路径

### 修复的一个真实缺陷

爬虫预检失败时以退出码 2 结束，并把诊断写进 `--json-out`；但工作台在非零退出时
**直接走失败分支、不读结果文件**，于是「缺浏览器 / 档案被占用 / 未登录」这些真正
原因永远到不了界面。已改为失败路径也读诊断。

实测（制造真实 profile 锁）：界面显示
「✗ 浏览器档案正被另一个浏览器占用 → 请先关闭登录窗口…」，样式为警示。

## 5. 不得往安装目录写字节码

随包运行时位于安装目录，写 `__pycache__` 会污染安装目录，且**卸载不会清理**
这类「安装后新增」文件（不在 MSI 组件表里）。

spider 模块有**两处**启动随包解释器，都必须带 `-B`：

1. `SpiderRunner.run`（抓取时）
2. `check_environment`（**应用启动时的依赖探测**）

第 2 处曾被遗漏，导致安装后文件数 2693 而 MSI 清单为 2680；清理后回到 2682，
再启动一次又变回 2693。

实测对照（同一份 `cli.py`、同一随包解释器）：

| 运行方式 | `__pycache__` |
|----------|---------------|
| 带 `-B` + `PYTHONDONTWRITEBYTECODE=1` | **0** |
| 不带任何保护 | **1** |

测试已改为 **AST 静态扫描**：遍历模块内所有「以 python 解释器变量开头」的
`subprocess.run`/`Popen`，任何一处缺 `-B` 即失败（原先只断言「源码里出现过 -B」，
太弱，正是它放过了第二处遗漏）。

## 6.1 用户实测反馈后的两处修复（档案占用 / 扫码登录）

用户截图反馈两个现象，排查后确认是**两个独立缺陷**，都已修复：

### 缺陷 A：档案占用判定在 Windows 上恒为 False，报错又恒为 True

**现象**：日志反复出现 `✗ [profile_locked] 浏览器档案正被另一个浏览器占用`；
而界面上从不提前警告，用户点下去才失败。

**根因**：两处判定（工作台 `spider.profile_in_use`、爬虫
`diagnostics._profile_locked`）都靠"打开 `Default/LOCK` 看会不会失败"，
而 Windows 上它是 **0 字节普通文件，可反复打开**，判定恒为 False；反过来，
崩溃残留的 `SingletonLock` 又让判定恒为 True，把用户永久挡住。

**修复**：新增 `core/profile_lock.py`（工作台有逐字副本，由
`tests/test_spider_profile_lock.py` 断言一致），改为**按进程判定**：

- 只有「命令行里带该档案目录的活浏览器进程」才算被占用；
- 有锁文件但没有活进程 = 崩溃残留，**自动清理**并给出提示，不再阻断用户；
- 探测链短路：psutil → wmic → PowerShell CIM，任一条给出结论即采信。

> **实现过程中发现并修掉的第二个坑**：Chromium 只把档案目录写成
> `--user-data-dir=<路径>`，早期实现拿**整个参数**去做路径规范化，于是它变成
> `<当前目录>\--user-data-dir=c:\...`，**永远匹配不上**，探测实际恒为
> 「未占用」。已改为识别带前缀形态，并有真实浏览器占用的端到端验证
> （`tools/verify_profile_lock_e2e.py`、集成用例
> `test_detects_real_browser_holding_profile`）。

### 缺陷 B：打包版的扫码登录按钮是坏的

**现象**：点「抖音登录」提示
`爬虫组件加载失败：No module named 'DrissionPage'。请安装爬虫依赖（DrissionPage 等）。`

**根因**：扫码登录在**应用进程内**执行
`from core.browser_manager import BrowserManager`，而它 `import DrissionPage`；
PyInstaller 的静态分析看不到这种运行期动态导入，`jingxu.spec` 既没有
`hiddenimports` 也没有 `collect_all`，**DrissionPage 根本没被打进包**。
源码运行正常，只有装机版失败——而提示语又把"打包漏收集"误导成"请安装依赖"，
用户在已安装的 MSI 里照做无从下手。

**修复**：

1. `jingxu.spec` 用 `collect_all` 显式收集 DrissionPage 及其运行时依赖
   （lxml / websocket / cssselect / tldextract / filelock / psutil）；
2. 报错文案区分「缺组件（并说明怎么装）」与「浏览器启动失败（附类型、浏览器
   路径、档案路径）」；
3. 新增 `tests/test_packaging_login_deps.py` 把「登录所需模块」与「spec 收集
   范围」绑成断言——以后新增登录依赖却忘了写进 spec 会直接失败；
4. 档案被占用时，登录/抓取**在启动浏览器之前**就拦住并说明是哪个进程。

### 未验证部分（重要）

**真实抖音/快手抓取无法在本机验证**，原因：

- 需要登录态与真实对标账号；
- 两个平台均有反爬，且页面结构随版本变化。

因此以下内容**未经真实页面检验**：

- 新增的候选字段路径是否覆盖当前线上结构；
- 全树扫描在真实数据上的召回与误报表现；
- 商品价格单位（分/元）判断在真实数据上的正确率。

**可以确定的改进**：即使仍然抓不到，现在会明确给出
「已知路径为空 / 扫描了 N 个节点 / M 个候选 / 属于哪类结论」，
并保留完整原始输出，使问题可定位——这正是重写要解决的核心问题。
