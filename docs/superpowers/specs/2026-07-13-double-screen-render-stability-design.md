# 双屏特效与渲染稳定性设计

> **存档（2026-09-23）：** 本文以 .NET/WPF 时期的路径与类型为证据，该参照树已移除（git 标签 `last-dotnet-reference`）。现行技术栈为 Python（`src/JingXu.Workbench.Py`），文中 `.cs`/`.xaml` 路径仅作历史记录。

## 目标

在不改变现有页面布局、配色和控件样式的前提下，解决截图中的三个问题：任务渲染失败、渲染速度慢，以及缺少可指定起始片段的上下双屏特效。

## 交互约束

- 在现有“随机画面变化”效果开关行中，使用相同的 `CheckBox` 样式增加“双屏”。
- 双屏开启后，在同一区域显示“从第 N 个视频开始（至结尾）”选择项。
- “第 N 个视频”按最终成片编排序列计数，而不是按素材列表编号计数。
- 原画、画幅、蒙版、贴纸、字幕、BGM 和已有随机效果的交互及样式保持不变。

## 渲染设计

- 双屏设置作为渲染请求的独立不可变快照，不混入随机效果模板。
- FFmpeg 在每个片段完成现有画幅适配后，再判断该片段是否达到起始位置。
- 生效片段将同一画面分成两个分支，每个分支缩放并居中裁剪为完整画布的一半高度，最后使用 `vstack` 上下拼接。
- 未达到起始位置的片段继续走原有画面链路；所有片段仍按原顺序 `concat`，因此时长和音频不变。

## 稳定性与性能

- 复杂软件滤镜链不再强制加入 `-hwaccel auto`。当前输出编码器是 `libx264`，自动硬件解码在部分 Windows 驱动/FFmpeg 组合上会产生硬件帧与软件滤镜不兼容，表现为直接渲染失败。
- 默认不自动勾选耗时明显的 `hqdn3d` 降噪；原有降噪开关和效果继续保留，用户仍可主动启用。
- 执行失败时从 FFmpeg stderr 中提取最后一条有实际原因的错误，而不是只显示末尾的 `Conversion failed`。

## 验证

- 单元测试确认双屏只对起始片段及之后片段生成 `split`/`crop`/`vstack`。
- 单元测试确认复杂滤镜转码不再包含 `-hwaccel auto`，默认降噪为关闭。
- ViewModel 测试确认起始位置随任务入队形成快照，且不会改变现有控件状态。
- 运行 Release 构建、相关测试、发布到 `dist`，最后执行 `JingXu.Workbench.exe --self-test`。
